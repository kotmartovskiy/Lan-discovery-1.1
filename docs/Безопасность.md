# Безопасность

Модель доступа и hardening панели LAN Discovery (актуально на
30.09.2026, PHASE 14). Общая структура — [Архитектура](Архитектура.md),
каталог роутов и колонки «Доступ» — [API](API.md).

## Модель доступа

- **Роли:** `admin`, `editor`, `guest` (поле в `users.json`);
  проверки — декораторы `@login_required`, `@admin_required`,
  `@can_edit` в `modules/auth.py`. Пароли — **bcrypt**.
- **Сессии** Flask (cookie, `SECRET_KEY` из
  `/etc/lan-discovery/secret.key`).
- **CSRF** — глобальный `CSRFProtect` (`app.py`), `@csrf.exempt`
  нигде не используется:
  - формы — скрытое поле `csrf_token`;
  - JS — `<meta name="csrf-token">` в `base.html`/`base_app.html` и
    fetch-обёртка сама ставит заголовок `X-CSRFToken`;
  - анонимный `POST` без токена → **400**, без сессии → **302** на
    `/login` (проверяется live-тестами `tests/live/test_live_smoke.py`).
- **Открытые роуты — ровно 3** из 163: `GET/POST /login`,
  `GET /logout`, `GET /api/health`. Всё остальное требует сессию;
  опасные операции (перезагрузка, управление пользователями и
  сервисами, бэкапы/restore, диск, сбросы) — только `admin`
  (40 роутов под `admin_required`).

## Секреты и чувствительные файлы

| Что | Где | Примечание |
|---|---|---|
| `users.json` | `/etc/lan-discovery/` | логины + bcrypt-хеши |
| `secret.key` | `/etc/lan-discovery/` | Flask `SECRET_KEY` (CSRF/сессии) |
| `secrets/`, `notes/` | `/etc/lan-discovery/` | пользовательские «секреты» и заметки (файлы) |
| `settings.json` | `/etc/lan-discovery/` | настройки панели, включая сетевые |

Права: каталоги держать `750`/`700` под сервисным пользователем.
`devices.db` не содержит паролей (только хеши в `users.json`).

## Периметр и транспорт

- Приложение слушает `0.0.0.0:8080` — доступно по LAN-IP и по
  WiFi-точке доступа; **TLS нет** (панель рассчитана на домашний LAN).
- **Dev-сервер Flask** (`app.run`) — для продакшена можно поставить
  gunicorn за reverse-proxy (см. [Архитектура](Архитектура.md)).
- Firewall/VPN (WireGuard/tailscale) — на стороне хоста; панель
  не открывает портов наружу сама.

## Модель угроз — «root by design»

Сервис намеренно работает **от root**: панель управляет systemd
(`/api/service/...`), дисками, клонированием eMMC, bluetooth/wifi,
сетью и содержит веб-терминал + файловый менеджер с корнем `/` —
по модели «admin-доступ = root-доступ к хосту» (см. также
[Архитектура](Архитектура.md)). Компенсации:

- вход — только по роли `admin` (bcrypt + сессии с TTL),
  терминал/filemanager — `@admin_required`;
- панель не выходит за пределы LAN (нет TLS, порт не пробрасывается);
- **systemd-хардening** в `deploy/lan-discovery.service` (применён на
  X96, PHASE 8): `PrivateTmp=yes`, `ProtectKernelTunables/Modules/
  ControlGroups=yes`, `LockPersonality=yes`, `RestrictRealtime=yes`.
  **Осознанно не включаются:** `ProtectHome` (filemanager/терминалу
  нужен доступ к `/root` и `/home`), `SystemCallFilter`/
  `CapabilityBoundingSet` (python + systemctl/диск/сеть/bluetooth —
  большой риск сломать функционал).

Альтернатива «non-root + gunicorn/reverse-proxy» отложена: требует
переработки SocketIO-прогона и sudo-моста для операций с системой
(см. §9, PHASE 8).

## Что уже сделано (hardening)

- Глобальный CSRF + csrf-meta во **всех** базовых шаблонах
  (включая вкладки `/apps/*` — правка P0/B6).
- `debug=False`, `TEMPLATES_AUTO_RELOAD` выключен (правка шаблона
  требует рестарта). Werkzeug dev-сервер используется осознанно
  (`allow_unsafe_werkzeug=True` в `socketio.run`) — см. «Модель
  угроз» выше.
- systemd-юнит с ограничениями (PHASE 8, см. «Модель угроз»).
- Security-тесты: `tests/unit/test_security.py` (заголовки/куки/
  аноним — гоняется в CI) и `tests/live/test_live_security.py`
  (регресс P1-10 против живой панели).
- `@login_required`/`@admin_required` на всех роутах (см. [API](API.md));
  новые роуты обязаны проходить review на декоратор.
- bcrypt вместо sha; пароли не логируются.
- Доки перед публикацией прогоняются через
  `python tools/sanitize_docs.py` (выход 0 = нет рабочих
  IP/паролей) → публичный репо `Lan-discovery-docs`.

## Известные ограничения (осознанные риски)

- **Нет TLS и rate-limit** на `/login` (brute-force из LAN возможен) —
  смягчается изоляцией сети; при необходимости — fail2ban/iptables
  на хосте.
- **SocketIO-события не покрываются CSRF** — смягчено same-origin
  политикой браузера и session-auth; принимать события можно только
  с аутентифицированной сессией.
- **Dev-сервер** не рассчитан на большую нагрузку/интернет.
- `admin`-роуты управляют ОС (reboot/poweroff, запуск сканов,
  управление systemd) — компромисс admin-пароля = компромисс хоста.
- Restore из UI (`/system/db-restore`) пишет в рабочую БД — перед
  restore сверять имя файла; полный restore-процедура —
  [Восстановление](Восстановление.md).

## Чек-лист при изменении кода

1. Новый роут → `@login_required` (опасный — `@admin_required`).
2. Мутирующие вызовы из JS → через fetch-обёртку (токен подставится).
3. Секреты/пароли — не коммитить; в доки — только плейсхолдеры.
4. Перед push — `python tools/sanitize_docs.py` (если менялись доки).
5. Тесты — `pytest tests/unit` (+ `tests/live` при живой панели):
   аноним-поведение (302/400) проверяется автоматически.
