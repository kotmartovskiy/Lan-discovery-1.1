# Восстановление из бэкапов

Проверенная процедура (PHASE 11, дрил 30.09.2026: PASS — боевые данные
не затронуты, восстановление в изолированный префикс + идемпотентность).

## Что и где лежит

| Источник | Кто создаёт | Куда | Содержимое |
|---|---|---|---|
| БД + конфиг | таймер `backup-db.service` (cron-подобный, ежедневно) и вручную `backup-db.sh` | `/srv/backup-db/` | `devices_*.db` (sqlite-копия через `.backup()`), `config_*.tar.gz` (архив `/etc/lan-discovery`: settings.json, users.json, secret.key, …) |
| Код | `update.sh` перед обновлением | `/var/backups/lan-discovery/<YYYYMMDD-HHMMSS>/` | `code.tar.gz`, `settings.json`, `devices.db`, `meta.json` |

Ротация: `/srv/backup-db` — 14 дней (оба паттерна), `/var/backups` —
`--keep` (default 5) при каждом `update.sh`.

Важно: список бэкапов в UI (вкладка «База данных») фильтруется по
`devices_*.db` — `config_*.tar.gz` там **намеренно не показывается**
(восстанавливаются через `recovery.sh`).

## Восстановление на рабочей системе

```bash
# 1. Посмотреть, что найдёт auto-pick (последние бэкапы):
sudo ./recovery.sh --dry-run

# 2. Полное восстановление (код + БД + конфиг + юнит + рестарт + health):
sudo ./recovery.sh

# 3. Частичные случаи:
sudo ./recovery.sh --db /srv/backup-db/devices_20260930-233341.db   # только БД
sudo ./recovery.sh --no-restart                                     # без рестарта
sudo ./recovery.sh --config-tar /srv/backup-db/config_20260930-233341.tar.gz
```

Флаги: `--db`, `--code-tar`, `--config-tar`, `--config-dir` (default
`/etc/lan-discovery`), `--prefix` (default `/opt/lan-discovery`),
`--unit` + `--unit-dir` (пересобрать systemd-юнит под `--prefix`),
`--no-restart`, `--dry-run`.

## Восстановление на чистую систему

```bash
# 1. Сначала поставить скелет (venv, юнит, каталоги):
sudo ./install.sh

# 2. Затем накатить данные из бэкапов (перезапишет код, БД и конфиг):
sudo ./recovery.sh --unit

# 3. Проверка:
systemctl status lan-discovery
curl -fsS http://127.0.0.1:8080/api/health
```

Бэкапы должны лежать на диске/шаре по стандартным путям — заранее
скопируйте `/srv/backup-db/` и последний `/var/backups/lan-discovery/<ts>/`
на носитель.

## Что проверяет recovery.sh автоматически

- `python3 -m py_compile` для `app.py`, `core/*.py`, `modules/*.py`;
- sqlite: `PRAGMA integrity_check`, `user_version`, `COUNT(*) devices > 0`;
- при обычном запуске: `systemctl restart` + health-чек до 60 с.

## Дрил (как в тесте PHASE 11)

```bash
sudo ./recovery.sh --prefix /tmp/lanrec --config-dir /tmp/lanrec/etc \
     --unit --unit-dir /tmp/lanrec/unit --no-restart
# ожидаемо: rc=0, SYNTAX OK, DB OK, settings.json md5 == боевому;
# повторный запуск идемпотентен; /etc и БД боевой системы не тронуты
```

## Troubleshooting

- **«нет code.tar.gz в /var/backups/lan-discovery»** — обновлений ещё не
  было; укажите `--code-tar` вручную или поставьте `install.sh`.
- **«нет бэкапов devices_*.db»** — таймер не срабатывал; запустите
  `sudo /usr/local/sbin/backup-db.sh` и проверьте
  `systemctl list-timers backup-db*`.
- **health не прошёл** — `journalctl -u lan-discovery -n 50`;
  откатить можно `update.sh --rollback` (если бэкап есть) или повторить
  `recovery.sh` с заведомо целым бэкапом.
- **конфиг восстановлен, но сервис видит старые настройки** —
  `systemctl restart lan-discovery` (файл settings.json читается при старте).
